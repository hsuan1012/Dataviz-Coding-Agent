# 多層次驗證

核心風險是**視覺幻覺（hallucination）**：圖看起來對、其實數值錯置。對策是**一律以實際執行程式與數值校驗取代模型臆測**。以下五層，全通過才視為達標。

## ① 程式層

確認產出程式能正常啟動、無語法/執行錯誤，並通過靜態檢查與單元測試。

- 執行 build / dev（`npm run build` 或起 dev server）確認無錯。
- 跑 linter（oxlint / eslint）與 `vitest`。
- 注意 JSX 需用能解析 JSX 的工具驗（`node --check` 認不得 JSX；用 Vite 的 `transformWithOxc` 或直接 build）。

## ② 資料層（最關鍵，防資料錯置）

以**已知答案的測試資料**校驗統計量與圖形對應數值，確保無資料錯置。

- 用一份你手算得出答案的小資料餵進去，檢查圖上的值 == 手算值。
- 檢查：總和、最大/最小值落在正確的類別上、排序正確、缺失值處理沒把 0 和「無資料」混淆。
- 排名/排序遇到**同值**時要有明確規則（同分應同名次，而非依資料順序隨機給名次），並用一組含同值的資料實測。
- 跨期（多年度）資料：硬檢核**每期實體集合完全相同**（改制、改名會讓實體換鍵後無聲消失）；已知官方總數的年度當**錨點**整批比對。
- 有聚合層級時，抽查「上層值＝下層加總」，且比率類欄位（密度、增率）必須**重算**而非平均下層值。
- 階層圖（treemap/sunburst）：驗「全國＝Σ縣市＝Σ鄉鎮」的**逐層加總自洽**，並抽查 tooltip 的「佔上層比例」＝ node/parent 重算值。
- API 對**空資料庫/未 seed** 寫一個測試：應回明確空值（空清單），不是 500。
- 存量+流量並存的資料（人口＋出生/死亡/遷移）：驗**恆等式「Δ存量＝Σ流量分解」**
  （如 月底人口−上月底＝出生−死亡+遷入−遷出）——比單錨點強得多；能取得另一個
  已驗資料集的同一統計量時，加**跨資料集錨點**。
- 完整性檢核要驗到**「(期別, 實體) 組合」層級**，不只「期別存在」——單一實體缺列
  時，檢核本身要回報錯誤清單而非在後續計算中 KeyError 崩潰（檢核函式的契約是
  「回傳錯誤」，用「餵缺列資料」的測試保護它）。
- choropleth 特別檢查：行政區名有沒有正確對應到地圖 feature（「臺 vs 台」、改制、全形空白是常見錯位來源）；顏色深淺對應的數值方向正確。

## ③ 互動層

用 **Playwright** 自動操作介面（篩選、縮放、懸停），驗證互動行為正確。

```js
// 例：hover 顯示 tooltip、點 legend 切換系列、filter 後資料點數改變
import { test, expect } from '@playwright/test'
test('hover 顯示 tooltip', async ({ page }) => {
  await page.goto('http://localhost:5173')
  await page.locator('canvas').hover()          // 觸發 hover
  // 依實作斷言 tooltip 內容 / DOM 變化
})
```

- 驗篩選後資料真的變、hover 顯示的數字正確、連動（linked）圖表同步。
- 有「選取/高亮」狀態時，檢查高亮外框不會被相鄰元素的邊框蓋掉——SVG 沒有 z-index，後畫的蓋先畫的，選取框應以 overlay 方式最後渲染。
- **d3.brush 與 hover tooltip 共存**：brush 的透明 overlay 會蓋住資料元素、吃掉 mousemove → tooltip 全滅。解法：掛好 brush 後把資料層 `raise()` 到 overlay 之上——從空白處起拖＝框選、從資料元素上按下＝hover，兩者並存。另外程式化清框（`brush.move(null)`）會再觸發 `end` 事件，handler 開頭要用 `if (!ev.sourceEvent) return` 擋掉，否則清框會把剛存好的選取結果覆蓋掉（無限迴圈或自我清除）。
- **點擊「小型/不規則形狀」元素（地圖小鄉鎮、細長 path）用 `dispatchEvent("click")`，別用真滑鼠**：Playwright 的 `.click()` 會點元素 bbox 中心，但凹形/細長 path 的 bbox 中心常落在**鄰近元素**上（實測：迷你地圖點某鄉鎮、事件落到隔壁鄉），測試就默默點錯對象。驗「點了會發生什麼」的語意時，`locator.dispatchEvent("click")` 直接對目標元素派發冒泡事件（React 委派照常接到），不受幾何形狀影響。例外：驗 hover 進出（mouseenter/mouseleave）要真實滑鼠軌跡才可信——改移到「該群組中面積最大的 path」的 bbox 中心（用 `getBoundingClientRect` 逐一算面積挑最大），大面積形狀的 bbox 中心幾乎必落在自身內。
- **隱藏/移除 UI 元素時，同步全域掃驗證腳本裡引用它的舊斷言**：實測案例：資料層把某年份設為隱藏（HIDDEN_YEARS）後，一支既有 Playwright 回歸腳本仍在點該年份的按鈕——腳本在 main 上就會 timeout，卻是在無關的新功能分支跑回歸時才炸出來，極易誤判成新工作引入的回歸（要花一輪 `git diff main` 才能自證清白）。守則：改掉任何使用者可見元素（年份、選項、按鈕文字）時，grep 所有 verify/test 腳本裡的舊值一併更新。
- **合成框選（d3.brush）拖曳測試，起訖點別直接對準某個資料標記的座標**：資料層常被 `raise()` 疊在 brush overlay 之上（見上一條，為了讓 hover 與框選共存），這代表把拖曳起訖點精準設在某個標記（如某顆泡泡）的畫面中心，命中的其實是那個標記本身而非 brush 的透明 overlay（同層兄弟節點，事件不會互相穿透）——brush 完全不會啟動、`ev.selection` 恆為 null，測試斷言默默失敗，容易誤判成產品邏輯壞了。守則：合成拖曳矩形用跟資料無關的固定小範圍（不刻意對準任何一個標記），或至少留夠大安全邊距（大於圖上最大標記的半徑）。
- **多個連動視覺共用同一份「篩選/勾選」狀態時，該狀態為空不等於「沒東西可畫」**：常見直覺是「使用者一個都沒勾，那就沒東西好顯示」，讓每個連動視圖（地圖/散布圖/長條圖等）各自獨立切成空白提示文字或完全不渲染——實測一個三視圖連動的 app（choropleth 地球儀＋散布圖＋排名長條圖）原本正是這樣，全部取消勾選後地球儀變空白海洋、散布圖只剩一行提示字。更好的預設：**全部項目仍照樣畫出來，只是統一套用一組中性色（灰階／白底黑邊）取代語意色（洲別色／指標色階）**——使用者仍看得到「全貌骨架」，「準備好開始篩選」在體驗上比「畫面整個消失」更順。實作上優先在呼叫端（元件層）加一個 `isNeutral = selection.size === 0` 分支去**短路**顏色 accessor 的回傳值，不要動已經有完整測試覆蓋的底層純函式（如 region→顏色的映射）——中性色只是「這次不要走語意色那條路」，不是那條路本身壞了，短路寫法讓既有單元測試不用改一行仍全綠。驗證時要逐一視覺確認**所有**連動視圖的中性色是同一套語言（不能地圖白底黑邊、散布圖卻用另一種灰階，語意不一致等於沒講清楚）。
- **驗證篩選/框選涵蓋範圍時，別用「資料自己的 min/max 對半切」決定測試矩形**：真實資料常嚴重偏態（如絕大多數值集中在低值區、只有零星極端值），用資料實際極值算出的兩個對半矩形，其中一半可能就框到近九成的點——原本想證明「兩次不重疊框選＝累加不取代」的測試，因為每一半都幾乎涵蓋全部資料，反而讓後續「還有未選中的點」「調暗顆數>0」之類的斷言全部失真。守則：優先用實際跑過、驗證過「各自非空、加總不到全部」的固定小範圍（screen-fraction 座標），或改讀 DOM 目前實際狀態（如當下所有「已選中」標記的真實 `getBoundingClientRect()` 聯集）動態算出涵蓋範圍，別假設合成的幾何切法在任意資料分布下都成立。

- **對數/非線性軸（log/symlog）的滾輪縮放與拖曳平移，一律在「刻度轉換空間」計算，且縮放中保留原刻度型態**：縮放數學若在「資料值空間」保持錨點比例（t=(anchor-lo)/width），隱含假設「值比例=像素比例」——只對線性軸成立。對數軸上游標像素位置對應的值比例差距極大（游標在畫面正中央，值卻只佔線性全域的 3%），想硬把錨點釘在游標像素，新 domain 必須延伸出全域範圍（如負的人均所得），被邊界 clamp 推回後錨點必然跳走——**「縮放中把對數軸切成線性刻度」與「游標指哪放大哪」在寬對數軸上數學上不可兼得**，別試圖用更精細的錨點公式打補丁。正解：把 domain/anchor 先過刻度的正轉換（log→`Math.log`；symlog→`sign(x)*log1p(|x|/C)`，C=scale 的 constant），在轉換空間跑同一套線性縮放/平移數學，再反轉換回資料值；轉換空間裡「值比例=像素比例」正是該刻度映射像素的方式，錨點像素級釘住（實測 0px），縮放中軸保留 log/symlog 刻度（刻度值改動態現算），恆等轉換=線性軸行為完全不變，可寫成一個泛用的 `zoomDomainInSpace(current, full, anchor, factor, fwd, inv)`。**移植警示**：「已知且可接受的邊界誤差」這種 YAGNI 判斷是**綁定原專案資料範圍**的——實測案例：symlog 軸（constant 2000、域窄）上值空間縮放的錨點偏移小到被標註「可接受、不修」，同一套程式逐字移植到三個數量級的真對數軸（300–250000）後，同一個誤差放大成半個繪圖區的跳躍（282px），而移植時連註解和 YAGNI 判斷一起照搬、無人重新評估。守則：移植帶有「已知可接受誤差」註記的程式時，用新專案的資料範圍重算該誤差的實際大小，別假設原判斷可攜。
- **錨點/位置類互動的 e2e 驗證，抓「基準位置」前要等前一個動作的補間動畫完全結束**：驗「游標下的元素縮放後不跳走」這類斷言，流程通常是「還原→抓元素位置當基準→操作→比對」。若還原本身也帶補間（如 750ms transition），抓基準時元素還在飛行中途，量出來的「漂移」是假的（實測：基準抓在還原動畫中途，誤報 213px 漂移；等補間結束再抓，真實漂移 0.8px）。凡量測前的**每一步**狀態改變（還原、切換、載入）都要等其動畫時長＋餘裕再取樣，不是只有被驗的那一步。

### 進場/切換動畫：靠「逐毫秒量測」驗，別看定格截圖

動畫「其實沒跑」是靜態驗證抓不到的坑——tsc、單元測試、甚至**動畫結束後的截圖**都會通過（最終狀態正確）。驗動畫要用 Playwright 在觸發後**分時間點取樣實際樣式值**（如逐格量 `getComputedStyle(el).width`），確認它是「由起點漸變到終點」而非瞬間跳到終點。

- **「從 0 長出」類進場動畫要用雙重 `requestAnimationFrame`**：在 `useEffect` 直接把值從 0 設成目標，React 會把「0」與「目標」併進同一次繪製，瀏覽器只畫最終格 → CSS transition 不觸發、元素瞬間到位。正確做法：先渲染起始值（0），`requestAnimationFrame(() => requestAnimationFrame(() => 設目標值))`，讓瀏覽器先畫出起始格、下一格再改值，transition 才會跑。實測佐證：修前逐格量寬度恆為 212px（瞬間滿）；修後 `0→1.5→65→192→212px`（約 600ms 漸長）。
- **資料 lazy load 時，進場動畫要綁「資料抵達」而非「元件掛載」**：若圖表資料是點擊後才非同步載入（地圖分區、村里圖資等），把動畫綁在 mount 會太早——等資料真的來、元件重繪出內容時動畫早已跑完 → 一樣瞬間到位。改綁在「資料列首次出現」（如 `rows.length > 0 && 尚未播過`）才啟動。實測佐證：綁 mount 時村里長條全程 0px（動畫在資料到達前就跑完）；改綁資料抵達後 `0→5→120→294→314px`。
- **切換的識別 key 要選對**：用穩定 key（如實體名）讓「同一批、值變化」（如切年份）走平滑補間；用會變的 key（如層級）強制 remount 讓「換一批」（如下鑽換層）重播進場。混用會讓不該重播的誤觸、或該重播的不動。
- **一律尊重 `prefers-reduced-motion`**：偵測到就直接定位、不播動畫（初始 state 即為終點值，跳過 rAF 與 transition）。

### 離散步進動畫改「連續播放」：資料內插＋改造順序決定每個 commit 都可用

時間軸播放若用 `setInterval` 每 N ms 跳一格整數時點（年/月），觀感就是「一張張圖輪播」。連續化的正解不是 CSS transition 補間（顯示端仍整數跳動、且會拖慢縮放等其他互動），而是 **rAF 驅動「小數時點」＋資料層內插**：

- **播放迴圈**：`requestAnimationFrame` 以真實幀間隔 dt 推進小數時點（速度=原步進速度換算，總時長不變），effect 依賴只掛 `isPlaying`、當前時點走 ref 鏡射——不隨每幀重啟 effect，也不受 React render 耗時拖慢播放速度。推進邏輯抽純函式（`advance(current, dtSec, speed) → {value, done}`）可單元測試。
- **內插層**：對前後兩個離散時點**逐欄位線性內插**；任一側缺值→該欄位 null（不捏造資料，照既有缺值規則隱藏）；布林/旗標類欄位取 floor 時點；**整數時點 fast path 直接回原始紀錄 reference**——未播放時行為與改造前 bit-for-bit 相同，既有測試就是回歸網。索引用 `Map<實體, Map<時點, 紀錄>>`＋WeakMap 以來源陣列為 key 快取，多元件共用不重算。
- **改造順序是成敗關鍵**：先鋪內插層、讓**所有**時點消費端支援小數（顯示端一律 `Math.floor`：滑桿、浮水印、tooltip、輸入框、排名查表），**最後**才把驅動迴圈換成 rAF。反過來先切迴圈，凡是 `r.time === current` 精確比對的消費端會整批查無資料（實測：泡泡整批消失）。照這個順序，每個 commit 都保持 app 可用。
- **驗證**：播放中分時取樣同一元素的位置，斷言「**同一個顯示整數時點內**」位置仍持續變化（內插真的生效），而不是只驗時點有前進——後者對「一格格跳」的舊行為也會過。

### e2e 驗證腳本自己也會腐化：寫死座標、字面樣式值、與新設計相牴觸的斷言

app 改版時 e2e 腳本不會自己跟上，且失敗訊息看起來像 app 壞了。先在瀏覽器**手動重現同一操作**分辨「app 真壞」vs「斷言過期」，再決定修哪邊。實測踩過的四種腐化：

- **寫死的互動起點座標**會因資料/預設軸/元素尺寸改版而「壓到」互動圖元上——框選起拖點壓在泡泡上，泡泡層在框選 overlay 之上（單擊 toggle 用），pointerdown 被泡泡吃掉→框選永遠選中 0 顆，app 完全正常。正解＝`document.elementFromPoint` 掃候選點清單，動態挑第一個沒壓到圖元的空白處起拖，對後續改版免疫。
- **字面樣式值斷言**（如 `fill='#CBD5E1'`）在樣式遷移成 CSS 變數後永遠 0 命中——改比對變數字串（React 會原樣寫進屬性，`fill='var(--token)'` 選擇子可用）或加專屬 `data-*` 測試鉤子（後者最穩）。
- **與新設計決策相牴觸的版面斷言**：矮視窗「出現整頁捲軸」若已是降級設計，舊斷言「無捲軸」就從回歸網變成永久誤報——改驗「降級真的生效」（如圖表列定高值），而非「舊版面還在」。
- **非決定性狀態要先定住再斷言**：rAF 播放暫停在「小數時點」，每次執行的暫停點都不同→下游幾何斷言間歇性誤中（偶爾有實體恰好落在公差內）。斷言前顯式把狀態設回固定值（如時間輸入框設整數年）；公差選「能精確區分 bug 特徵」的值——clamp 釘邊的特徵是**恰等於** range 端點，0.01px 照樣抓得到回歸，0.5px 反而誤傷自然貼邊的資料點。

## ④ 視覺層

截圖與參考圖比對，檢查版面、配色、標籤一致性。

- Playwright `page.screenshot()` 擷圖。
- 檢查：有標題與軸標籤、圖例正確、配色確實來自樣式字典（不是隨機色）、無重疊裁切、深淺色模式都可讀。
- 圖例分級邊界不可重疊或含糊：相鄰級距共用的邊界值要明確屬於某一級（如「0–99 / 100–199」而非「0–100 / 100–200」）；整數資料用整數邊界。**浮點切點**（如 quantile 算出 2942.6）則用「X 以上，未滿 Y」的半開區間文案，且必須與程式的分級比較邏輯（`>=`）一致——別四捨五入再 -1，切點附近會顏色與圖例矛盾。
- **標籤對比**：檢查最深色階上的標籤是否可讀——標籤色要依填色深淺切換（labelLight/labelDark），一律深字在深底上對比會掉到 1.4:1。逐級抽一個實體看截圖。
- 地圖含 inset 或多投影時，逐一檢查**每個** feature 都仍可見、可 hover——面積懸殊的區域放同一個 inset 會被壓縮到看不見（例：烏坵鄉放進金門 inset 就會消失，需獨立 inset 或標記點）。這類問題截圖粗看不會發現，要對照 feature 清單逐一點名。
- **地圖主體要「填滿容器且置中」**：投影 bug（見 chart-selection「主島 fit 到固定視窗」「MultiPoint」）常讓主島縮成一角、大片空白。截圖要真的看主島有沒有填滿卡片；可用 DOM 量測 `d3.geoBounds(非離島FC)` 或投影後像素跨度是否接近畫布尺寸來自動化。
- **inset 島形要真的落在框內**：`fitSize` 只縮放不平移會把島畫到 SVG 原點、與方框脫節（框空、島跑左上角）。**自動化檢核**：用 `getBBox()` 取每個 inset 的島形 path union bbox，斷言它落在該 inset 方框範圍內（`x0>=box.x && y0>=box.y && x1<=box.x+box.w && …`）。這比肉眼看小方框可靠——縮圖時島形太小易誤判成「空框」。
- **沿用/移植既有投影邏輯時，「fit 排除集合、clipPath、繪製集合」是一組配套，只搬一半必越框**：主圖的 inset 通常是「fitExtent 時排除離群島＋clipPath 裁掉框外」兩道防線。移植到別處（如迷你地圖）若只搬了 fit、沒搬 clip、又照畫**全部** features，被 fit 排除的離群幾何就會投影到框外、疊在主圖上（實測：烏坵鄉在金門投影下飄到台灣本島海面上）。而 DOM 數量、高亮數等自動斷言照樣全綠——這類 bug 是靠**獨立審查比對「fit 用哪個集合、畫的是哪個集合」**抓到的。守則：繪製集合＝fit 集合（或補 clip），移植時逐項核對三件套；這與「inset 框不得與主圖相撞」同類，能形式化就寫成常駐檢查。
- **`flex-wrap` 容器裡「換行後只剩一個元素的那一行」，`justify-content: space-between` 不會把它推到列尾**：space-between 是靠「元素之間」分配空間，換行後若某一行只剩一個元素，沒有第二個可以「之間留白」，該元素會退回 flex-start（貼左），視覺位置跟同一列有多個元素時完全不同。實測案例：一排工具鈕在版面較窄時自動換成獨立一行，原本假設它「在列的最右側」而用 `right: 0` 幫它下面的彈出視窗定位，結果那一整行其實貼在最左側——彈出視窗算出的絕對座標整個算錯，一輪改成 `left: 0` 又因為沒改寬度上限，在另一種視窗寬度下換成右側被裁。**別靠印象或單一視窗寬度判斷 flex 子元素的實際位置**，要用 `getBoundingClientRect()` 實際量測（且要量測外層 `overflow: hidden` 祖先的邊界，不是只看直接父層），至少測兩種明顯不同的視窗寬度，才能抓出安全的絕對定位錨點與寬度上限。**後續需要「換行後獨佔一行的元素撐滿整行寬度」時，加 `flexGrow: 1` 是比重新量測寬度上限更根本的解法**：換行後它是該行唯一元素，flex-grow 會把它撐到跟整個容器同寬；沒換行、跟其他元素共用一行時，若容器本來就有 `justify-content: space-between`，`flexGrow: 1` 不會改變結果（不影響既有情境），且只要該元素本身沒設 `justify-content`（預設 `flex-start`），內部子元素的視覺位置也完全不受影響——用這招把可用寬度從「只到按鈕本身」擴大到「整行寬度」，比每次改版就重新量測安全邊界更一勞永逸。**若「相對某祖先絕對定位＋量測安全邊界」這條路線反覆修正多輪仍不穩定——甚至公式可證明自洽（如某個縮放係數理論上恆為 1）、大範圍視窗尺寸掃描也複製不出異常，使用者實際瀏覽器卻仍回報跑位——別再靠更精細的量測繼續打轉，改用 `createPortal` 把浮動內容整個搬到 `document.body`，用 `getBoundingClientRect()` 量出觸發元素座標換算成 `position: fixed`，直接跳出祖先鏈上任何一層 `overflow-hidden`／`clip` 的裁切範圍**：這類浮動彈出視窗（tooltip/popover/dropdown）的定位問題，本質上就是「相對定位鏈太長、任何一層裁切或量測時機差異都可能出錯」，portal 是消除整條依賴鏈的根本解，比在同一條路線上加量測、加安全邊界更可靠。若彈窗內容原本走「常駐 DOM、只切 `display:block/none`」（供既有測試腳本直讀 `textContent` 用），portal 化後仍可維持這個介面不變，只是選擇子要從「找 `position: absolute` 的祖先」改成「找 `position: fixed` 的祖先」，邊界斷言也要從「落在某張卡片內」放寬成「落在瀏覽器視窗內」（portal 後不再受那張卡片邊界限制，這才是重點）。
- **`flexGrow: 1` 撐寬容器後，若拿該容器的 `getBoundingClientRect()` 當浮動元素的定位錨點，必須同時給它 `justify-content: flex-end`（或等效的靠右手法），否則量到的右緣是「容器右緣」而非「裡面可見子元素的右緣」**：flexGrow 只改變容器本身占用的空間，不會改變容器內部子元素的排列方式——子元素仍依 `justify-content` 預設值（`flex-start`）貼容器左緣，容器右側因而多出一段肉眼難以察覺的留白（子元素之後、容器邊界之前）。若程式邏輯是「量這個容器的右緣，拿來當彈窗/提示框的 `right` 定位」，量到的會是容器右緣（偏右、留白外側），跟視覺上真正的按鈕群右緣對不齊——彈窗因此往右多跑一段，跟觸發它的按鈕脫節。實測案例：一排工具鈕（放大/選取/清除/使用說明）因 `flexGrow: 1` 撐滿整行寬度，但按鈕本身未加 `justify-content: flex-end`，導致按鈕群其實貼容器左緣、容器右側有大段留白延伸到繪圖區邊界；使用說明彈窗的定位量到的正是這段留白外緣，跟參考設計（按鈕群本身就貼齊角落）的視覺比對後才發現偏移。**教訓**：任何時候容器同時身兼「flex-grow 撐寬」與「子元素定位量測基準」兩個角色，都要親自確認子元素是否也設了對應的 `justify-content`，別假設「容器變寬≠子元素視覺位置改變」這句話在所有下游用途（含拿它當量測基準）都成立——它只保證子元素彼此之間的相對位置不變，不保證容器邊界=子元素視覺邊界。
- **版面類 bug 會通過 build＋單元測試**：這次投影/inset 兩個 bug 都是 tsc 綠、vitest 綠但畫面壞。務必做「實際開來看」這一步（human-in-the-loop 的價值點），並把能斷言的幾何（填滿度、落框）寫成 geo 測試固化。
- **尺寸由資料驅動的元素，貼近尺度上限時會溢出容器被裁**：任何大小綁在 scale 上的東西（泡泡半徑、圖例參考圓、長條），當資料值接近尺度最大值時，元素本身或其引線/標籤可能超出 SVG／容器邊界被切掉。實測案例：泡泡大小圖例的最大參考圓貼到半徑上限，圓頂拉出的「40,000」標籤超出 SVG 上緣被裁——**tsc/vitest/Playwright 全綠、AI 審預設情境截圖也沒發現**（預設圖例值沒到上限），是人把「大小」切到會頂到上限的指標、截圖才抓到。教訓有二：①容器尺寸要**預留元素在極值時的最大延伸量**（圖例基線下移、留出標籤空間），別按預設值抓高度；②**寫成回歸檢查**：斷言每個圖例/標記元素（尤其文字）的座標完全落在容器範圍內（`text.y - 邊距 >= 0` 等），並在測試裡**主動切到會觸發極值的指標**再驗，別只測預設狀態。
- **字級收斂檢查（機械式）**：掃描元件原始碼裡的裸數字字級，比對樣式字典的 `typography.sizes`
  清單——`grep -rnE "fontSize: ?[0-9]" src/ | grep -v styleDictionary` 應為空（或每筆都能對回
  字典值）。這條要**機械跑**而不是靠自覺：實測連照著流程走的迭代都會在加小元件（說明文字、
  提示章、小標籤）時臨場冒新字級，單日冒出三個孤兒字級（12/12.5/13.5）而截圖審查毫無感覺
  ——字級漂移是「每一張截圖各自看都好看」的累積型 debt，只有 grep 抓得到。發現孤兒字級的
  處置：併入既有字級，或在字典裡命名新角色後改引用。
- **圓角/元件樣式收斂檢查（機械式，同上原理）**：`grep -rnE "borderRadius: ?[0-9]" src/ |
  grep -v styleDictionary` 應為空——圓角一律從 `components.*.radius` 取。實測同一 app 累積
  7 種圓角散落 21 處、tooltip 樣式複製兩份。凡是「值由設計決策而非資料決定」的屬性
  （圓角、元件內距、陰影），都適用「字典具名＋grep 歸零」這套；資料驅動的值（scale 輸出、
  座標）則不在此列。
- **「量測定高」圖表沒有內在高度——鎖屏版面的矮視窗降級只能用「斷點＋定高」，不能用連續 min-height 地板**：svg 尺寸由 JS 量測容器決定（viewBox=量測值 1:1）的圖表，其高度對版面引擎而言是「別人給多少畫多少」，本身提不出最小需求。整頁 100dvh 鎖定的版面在矮視窗（高縮放筆電）會把這種圖壓成縮圖；直覺修法「給圖表槽 min-height 地板、讓內容自然撐開出捲軸」**必炸**——地板迫使拆掉定高鏈（height→minHeight），auto 高度環境下 flex-1 失去分配依據，svg 的量測值反過來變成內容高度，進入「量測→長高→再量測」回饋，實測連原本正常的桌機鎖屏都被撐破。正解＝**高度 media query 斷點**（如 `@media (max-height: 860px)`）：預設保持定高鎖屏鏈一字不動，斷點內整組切換成「root/main auto 高＋圖表列固定 px 高＋允許整頁捲軸」，並加 `scrollbar-gutter: stable` 防臨界高度捲軸現隱抖動。這與寬度斷點堆疊（fixed svg height）是同一套路：**降級版面裡凡是量測型圖表，高度必須給定值，不能留給內容協商**。驗證要補「寬而矮」情境（如 1920×800 捲軸出現＋圖表槽 ≥ 最小可讀高）與「斷點不誤觸發」情境（如 1920×1080 仍無捲軸）——RWD 驗證矩陣只掃寬度會漏掉這一族。
- **可形式化的視覺不變量，一律寫成數據檢查腳本，不要停在肉眼。** 驗證鏈「自動測試 → AI 審截圖 → 人類肉眼」**每一層都會漏**——實測案例：inset 框與主圖澎湖投影相撞，自動測試全過、AI 審全頁截圖也誤判，最後是人看局部截圖抓到。凡是「A 不得與 B 重疊」「島形須落框內」「主體須填滿容器」這類可以算的性質，就用與 app 相同投影邏輯寫 node 檢查腳本（例：逐 polygon 投影 bbox vs inset 框做矩形相交測試）納入驗證清單常駐執行；肉眼留給真正無法形式化的美感與語意判斷。

### Windows 開發環境：殭屍 process 是「畫面/檔案怪異但重現不了」的頭號嫌犯

- **殭屍 dev server**：被中斷的子代理或前一輪測試留下的 `vite`/`node` 程序繼續占著
  5173/5174 等埠，之後打開瀏覽器看到的是舊 HMR 狀態，容易誤判成「改的東西沒生效」
  或「出現詭異的舊資料」。Windows 下 `spawn` 出的 npm 程序樹要用
  `taskkill /T /F /PID <pid>`（或 spawnSync 呼叫它）才殺得乾淨，直接砍 node.exe 本身
  砍不掉子程序。
- **殭屍 esbuild/rollup 原生模組會鎖住檔案，刪資料夾會失敗**：跑過 `vitest`/`vite build`
  的目錄，`node_modules` 內的 `esbuild.exe`／`*.node` 原生模組可能仍在背景常駐（尤其
  vitest 的 watch/UI 模式），之後想刪除或搬移該資料夾（例如清掉已合併的 git worktree）
  會出現「Access denied」而非「路徑不存在」。用
  `Get-Process | Where-Object { $_.Path -like "*<目錄路徑片段>*" }` 揪出對應 PID
  砍掉（`Stop-Process -Id <pid> -Force`）後再刪，別急著懷疑刪除指令本身有問題。
- **共用 Playwright MCP 瀏覽器分頁會殘留前一個子代理/前一輪測試的自動化操作狀態**
  （例如框選名單、已展開的面板），截圖判讀前先 fresh reload 該分頁，避免把殘留狀態
  誤判成新一輪操作的結果。

## ⑤ 人工審查

依評分表（rubric）就正確性、可用性、美觀、互動體驗評分。這一層保留給人 —— 主動把成果與截圖交給人看，說明你驗了什麼、還有什麼需要人拍板。

## 自我修正迴路

驗證失敗時：**讀錯誤訊息 → 找根因（別亂試）→ 修正 → 重跑該層驗證**。重複直到通過或達重試上限（建議 3 次）後請人介入。修正時保持「內容與樣式分離」，別為了過驗證而在元件裡寫死樣式。

## 評分表範例（rubric）

| 面向 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 正確性 | 數值明顯錯置 | 大致對、少數偏差 | 全數與來源一致 |
| 可用性 | 難以理解 | 需說明 | 一看就懂 |
| 美觀 | 雜亂/配色亂 | 尚可 | 一致且精緻 |
| 互動 | 無效或報錯 | 基本可用 | 流暢直覺 |

## 視覺層檢核（方向 A）

- 對比：文字/標籤對其背景 ≥ AA 4.5（中間色調以 halo 保證）；提供 `relativeLuminance`/`contrastRatio` 工具實算，不臆測。
- 色階不變量測試：兩主題 densityScale 亮度單調、且皆不含紅（色盲安全）——列為回歸護欄。
- 深、淺兩主題各截一組圖（treemap/sunburst），確認標籤在兩主題皆可讀。
- 控制列整合檢查：檢視切換／breadcrumb／年度集中一條；圖表框進卡片；圖例帶級距與資料來源。
